## 1. Task Title
**Evaluation of Static, Dynamic, and Runtime Address Binding Paradigms for Enterprise Banking Systems.**

---

## 2. Problem Context
A banking institution maintains branch banking software deployed across 500 branch locations over a wide-area network (WAN). Currently, the application is compiled as a single 200 MB monolithic executable. Whenever a minor security patch or cryptographic compliance update is made to the internal encryption library, every branch location is forced to download the entire 200 MB executable. This incurs excessive network bandwidth (100 GB total), extended teller downtime, and operational risk.

---

## 3. Objective
To design, implement, and evaluate:
1. Static linking (`libcrypto_demo.a`) vs Dynamic linking (`libcrypto_demo.so`).
2. Address binding across compile-time, load-time, and execution-time.
3. Runtime symbol resolution via `dlopen()`, `dlsym()`, and `dlclose()`.
4. Process virtual address space inspection via `/proc/self/maps` and shared page deduplication.
5. Hot-patching capabilities without recompiling application binaries.
6. System fault tolerance during missing shared library events.

---

## 4. Concepts Involved
- **Compile-Time Address Binding:** Absolute or relocatable code generated by compiler/assembler.
- **Load-Time Address Binding:** Relocation records modified by dynamic linker (`ld.so`) when loading binary into memory.
- **Execution-Time Address Binding:** Dynamic virtual-to-physical address translation via MMU; dynamic mapping via `dlopen()`.
- **Linker vs. Loader:** 
  - *Linker (`ld`):* Resolves symbol references, builds ELF headers, and merges object segments (.text, .data, .rodata).
  - *Loader (`execve` / `ld.so`):* Allocates virtual address space, memory-maps segments, resolves runtime dynamic libraries, and transfers control to the entry point.
- **Position-Independent Code (PIC):** Machine code generated using PC-relative addressing (`-fPIC`), enabling the code segment to reside at arbitrary memory addresses and be shared among processes.
- **Global Offset Table (GOT) & Procedure Linkage Table (PLT):** Indirection structures enabling runtime PIC symbol resolution.

## 7. Compilation Commands
```bash
# Compile PIC object and build shared library
gcc -std=c11 -Wall -Wextra -fPIC -c libcrypto_demo.c -o libcrypto_demo.o
gcc -shared -o libcrypto_demo.so libcrypto_demo.o

# Build static library archive
gcc -std=c11 -Wall -Wextra -c libcrypto_demo.c -o libcrypto_static.o
ar rcs libcrypto_demo.a libcrypto_static.o

# Build static executable
gcc -std=c11 -Wall -Wextra crypto_static.c libcrypto_demo.a -o crypto_static

# Build dynamic shared executable with rpath
gcc -std=c11 -Wall -Wextra crypto_shared.c -L. -lcrypto_demo -Wl,-rpath,. -o crypto_shared

# Build runtime loading executable (requires libdl)
gcc -std=c11 -Wall -Wextra crypto_runtime.c -ldl -o crypto_runtime

# Build comparison metric tool
gcc -std=c11 -Wall -Wextra static_dynamic_comparison.c -o static_dynamic_comparison
```

## 11. Calculations
- **Bandwidth:** 
  $$\text{Static Update} = 500 \times 200\text{ MB} = 100,000\text{ MB} \approx 100\text{ GB}$$
  $$\text{Shared Library Update} = 500 \times 2\text{ MB} = 1,000\text{ MB} \approx 1\text{ GB}$$
  $$\text{Bandwidth Savings} = \frac{100,000 - 1,000}{100,000} \times 100\% = 99.0\%$$
- **Multi-user Memory:**
  $$\text{Static RAM for 50 users} = 50 \times 200\text{ MB} = 10,000\text{ MB} = 10\text{ GB}$$
  $$\text{Dynamic RAM for 50 users} = 1.8\text{ MB (shared code)} + 50 \times 0.2\text{ MB (private data)} = 11.8\text{ MB}$$

## 12. Experimental Investigation
1. **Size comparison via `ls -lh`:** Confirms static binary is ~52x larger due to embedded library code.
2. **`ldd` inspection:** Shows static binary has zero dependencies, shared binary depends on `libcrypto_demo.so`, and runtime binary depends only on `libdl.so`.
3. **Hot-Patching:** Executing `make patch_v2` updates `libcrypto_demo.so` to version `v2.0.0`. Running `./crypto_shared` immediately prints `v2.0.0` without recompiling the application binary.
4. **Missing Library Test:** When `libcrypto_demo.so` is renamed, `crypto_shared` crashes at launch (`error while loading shared libraries`). Conversely, `crypto_runtime` catches the error via `dlerror()` and continues running in fallback non-crypto mode.
5. **Memory Mapping:** `/proc/self/maps` verifies that `libcrypto_demo.so` is mapped as read-only executable (`r-xp`) page frames which are deduplicated across processes.

## 13. Evaluation
| Metric | Static Linking | Dynamic Shared Linking | Runtime Loading (`dlopen`) |
| :--- | :--- | :--- | :--- |
| **Disk Space** | Poor (duplicated in each binary) | Excellent (stored once on disk) | Excellent |
| **RAM Footprint** | Poor (duplicated per process) | Excellent (text segment shared) | Best (unmapped when idle) |
| **Startup Latency** | Fastest (~1.2 ms) | Moderate (~4.5 ms, ld.so resolution) | Fast initial launch (~1.1 ms) |
| **Patch Deployment** | High cost (200 MB re-download) | Low cost (2 MB patch) | Lowest cost (hot-reloadable) |
| **Fault Tolerance** | Self-contained | Fails launch if library missing | Highest (graceful degradation) |

## 14. Alternative Concept
**Lazy Runtime Loading (`dlopen`) Only When Needed:**
Instead of linking dynamically at program startup, the banking application loads `libcrypto_demo.so` only when a customer requests a secure cryptographic transaction.
- **Start-up Time:** Reduces initial application launch latency to bare minimum (no cryptographic GOT/PLT relocations during `execve`).
- **Memory Consumption:** Zero memory consumed during regular non-crypto banking operations (e.g. balance inquiry, account lookup).
- **Error Handling:** If `dlopen()` fails due to a missing or corrupted library, the core banking system logs an alert and continues servicing non-cryptographic transactions instead of crashing the teller terminal.

---

## 15. Time Complexity
- **Static Linking Resolution:** $O(S)$ where $S$ is the number of symbol entries (performed once at build time).
- **Load-Time Dynamic Resolution:** $O(R \cdot \log S)$ where $R$ is relocations and $S$ is dynamic symbols parsed by `ld.so`.
- **Runtime `dlsym()` Lookup:** $O(K)$ hash table lookup inside ELF `.gnu.hash` or `.hash` section ($O(1)$ average time complexity).

---

## 16. Space Complexity
- **Static Binary:** $O(N \cdot B)$ total disk space for $N$ applications embedding library size $B$.
- **Dynamic Shared Library:** $O(N \cdot M + B)$ where $M \ll B$ is the stub size, saving $O(N \cdot B)$ disk space and physical RAM.

---

## 17. Advantages
- **Dynamic Linking:** Massive bandwidth reduction during updates, shared physical memory pages across multiple users, independent component lifecycle.
- **Runtime Loading:** Eliminates startup dependencies, enables dynamic plugin architectures, isolates failures.

---

## 18. Limitations
- **Dynamic Linking:** "Dependency Hell" if shared library ABIs change incompatibly (breaking sonames); slight startup overhead due to dynamic relocation.
- **Runtime Loading:** Requires explicit pointer casting, error handling boilerplate, and manual lifetime management.

---

## 19. Conclusion
For the bank's branch software, **Dynamic Linking with Shared Libraries (`.so`)** should be adopted as the primary architecture. This reduces security update bandwidth by **99.0%** (from 100 GB to 1 GB across 500 branches) and enables instantaneous security patching without redistributing the 200 MB main binary. Furthermore, critical security modules should be loaded via **`dlopen()`** to ensure the teller terminal survives missing or damaged library files without taking the branch offline.
